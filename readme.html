01

System Overview

What This System Does

This is a fully autonomous drone vision system designed to run on a Raspberry Pi 4B. The drone uses its downward/forward-facing IMX708 camera to navigate a physical environment, find a specific QR-coded drop zone, verify it visually using template matching, and command a payload drop. All decisions are made purely from camera input — no GPS is used.

Mission Sequence

1. Drone searches for corridor walls using edge detection

2. Aligns and follows corridor toward target area

3. Detects green banner as waypoint marker

4. Scans for QR codes near the green marker

5. Reads START QR — extracts embedded template image

6. Matches all subsequent QR crops against that template

7. When confident match found and centred — issues DROP

8. Returns home and lands

Detection Methods Used

QR codes: pyzbar library for locating + decoding

Template matching: module-grid similarity + NCC + pixel diff

Green banner: HSV colour masking (hue 40–80°)

Red danger zones: Dual HSV range + solidity + aspect ratio filters

Corridor walls: Canny edge detection on ROI strip

Object detection: YOLOv8n (separate standalone script)

Image preprocessing: CLAHE, Gaussian blur, adaptive threshold, Otsu

Safety Design

Red zone override: Any red zone detection immediately overrides all other states and issues escape commands. If escape takes longer than 5 seconds, FORCE_EXIT is issued.

State timeouts: Every state has a maximum allowed frame count. If exceeded, the machine resets to SEARCH or forces LAND.

Template guard: DROP command is physically blocked unless visual template verification passes. Position alone is not enough to authorise drop.

Crash-safe planner: All planner calls are wrapped in try/except. Any crash silently disables the planner without affecting the main loop.

Temporal smoothing: Match result must be True for 3 consecutive frames before CONFIRMED MATCH is declared, preventing false positives from single-frame noise.

Temporal Smoothing — How It Works

Raw per-frame match results are noisy. A single bad frame can give a false positive or false negative. The smoothing window fixes this:

SMOOTHING_WINDOW = 3
match_history = []   # list of (found: bool, conf: float)

# Each frame where a candidate is evaluated:
match_history.append((best_found, best_conf))
match_history = match_history[-3:]   # keep last 3 only

# Confirmed match only if ALL 3 recent frames said True:
confirmed = (len(match_history) == 3 and all(m[0] for m in match_history))
avg_conf  = sum(m[1] for m in match_history) / len(match_history)

This means a match is only declared after 3 consecutive frames agree — roughly 100ms at 30fps. Single-frame flickers are ignored entirely.

Template Verification Guard (DROP protection)

The _verify_candidate() method is the single source of truth for visual matching. It is called in both TARGET_ALIGN and DROP_READY states. DROP is physically impossible without it passing.

def _verify_candidate(self, binary_crop, is_sharp):
    if self.target_data is None: return False, 0.0      # no template
    if self.qr_detector is None: return False, 0.0      # no detector
    if not is_sharp:             return False, 0.0      # blurry image
    if binary_crop is None:      return False, 0.0      # no crop

    found, conf = self.qr_detector.match_against_target(
        binary_crop, threshold=self.match_threshold)
    return found, conf

QR Tuple Normaliser

The mission controller accepts QR results in any tuple shape (2 to 6 elements) and normalises them all to the canonical 6-tuple before processing. This prevents crashes if the QR detector format changes.

# Accepted shapes → normalised to:
# (data, (cx,cy), rect, raw_crop, binary_crop, is_sharp)
2-tuple: (data, center)               → pad with None, None, None, True
3-tuple: (data, center, raw)          → pad with None, None, True
4-tuple: (data, center, rect, raw)    → pad with None, True
5-tuple: (data, center, rect, raw, bin) → pad with True
6-tuple: already canonical

How update_state Works

def update_state(self, new_state, reason=""):
    if new_state != self.state:              # only if actually changing
        self.prev_state  = self.state        # remember previous
        self.state       = new_state         # set new
        self.state_timer = 0                 # reset frame counter
        logger.info(f"[STATE] {prev} → {new} | {reason}")
    else:
        self.state_timer += 1                # increment if staying same

Note: timer only increments when staying in the same state. On transition it resets to 0. This means timeout logic counts consecutive frames spent in one state.

detectors/qr_detector.py — QR Detection + Matching

detectors/qr_detector.py

Role

Does three separate jobs: (1) locate QR codes in each frame using pyzbar, (2) decode the START QR payload which contains a base64-encoded image of the target, (3) visually compare candidate QR crops against that stored template using a module grid approach.

TargetData Dataclass

@dataclass
class TargetData:
    template_qr_image: np.ndarray  # binary 128×128 — used for matching
    template_qr_raw:   np.ndarray  # original decoded image — for debug saves
    timestamp:         str         # when it was loaded
    template_filename: str         # filename of saved processed copy
    payload_size:      int         # bytes of the encoded image

    def is_valid(self) -> bool:
        return self.template_qr_image is not None and self.template_qr_image.size > 0

Job 1 — detect() Per Frame Pipeline

1 → pyzbar.decode(frame) — finds all QR-shaped regions
2 → For each decoded object: check width and height >= QR_MIN_SIZE (50px)
3 → Calculate centre (cx, cy) and rect (x, y, w, h)
4 → _crop_qr() — crop with 8% margin padding, clamp to frame bounds
5 → _preprocess_template(raw_crop, denoise=True) — noisy path pipeline
6 → Append (data, (cx,cy), rect, raw_crop, binary_crop, is_sharp=True) to results

Note: is_sharp is always True in v2.0.0 — the sharpness_min parameter is accepted but Laplacian variance check is not yet wired to the return value.

Job 2 — load_target_from_qr_payload() Template Loading

1 → Receive raw text decoded from START QR by pyzbar
2 → _extract_base64(): strip data URI prefix (data:image/...;base64,) or custom prefixes (IMG:, TARGET:, TPL:, B64:)
3 → Validate: check length >= 100 chars (too short = not an image)
4 → base64.b64decode() → raw bytes
5 → Check magic bytes: PNG (89 50 4E 47), JPEG (FF D8 FF), BMP (42 4D), GIF (47 49 46 38)
6 → cv2.imdecode() → BGR image numpy array
7 → _preprocess_template(raw_img, denoise=False) — clean path (Otsu)
8 → Save raw + processed copies to template_dir with timestamp
9 → Return TargetData with template_qr_image, template_qr_raw, etc.

_preprocess_template() — Two Paths

CLEAN path (denoise=False) — for the START QR image:

→ BGR → grayscale
→ Otsu threshold (global)
→ _trim_quiet_zone() removes white border
→ resize to TEMPLATE_SIZE (128×128)
→ re-binarise at threshold 127

NOISY path (denoise=True) — for camera crops:

→ BGR → grayscale
→ GaussianBlur 3×3
→ CLAHE (clipLimit=2.0, tile=8×8)
→ adaptiveThreshold (Gaussian, block=11, C=2)
→ _trim_quiet_zone()
→ resize to 128×128
→ re-binarise at 127

Job 3 — match_against_target() Module Grid Matching

The core visual comparison algorithm. Compares two binary images by sampling them onto a coarse grid and counting how many cells agree.

grid_n = 29   # 29×29 = 841 cells

For k in [0, 1, 2, 3]:                       # rotations: 0°, 90°, 180°, 270°
    rotated = np.rot90(binary_crop, k)
    cand_grid = _image_to_module_grid(rotated, 29)   # 29×29 of 0/1
    tpl_grid  = _image_to_module_grid(template, 29)

    agree = count_nonzero(cand_grid == tpl_grid)
    conf  = agree / 841

best_conf = max across all 4 rotations
match_found = best_conf >= threshold (0.75)

Rotation checking handles QR codes that are rotated up to 270° — common in real flights.

_trim_quiet_zone() — Why It Matters

QR codes have a mandatory white quiet zone border. If this is included in the comparison, both template and candidate will have it and it artificially inflates the similarity score. By trimming it from both, only the actual QR modules are compared.

inv    = cv2.bitwise_not(binary)          # invert: dark modules become white
coords = cv2.findNonZero(inv)             # find all dark module pixels
x,y,w,h = cv2.boundingRect(coords)       # tight box around all modules
crop with 2px margin kept               # small border retained for safety

detectors/template_matcher.py — Advanced Visual Matcher

detectors/template_matcher.py

Role

A more sophisticated matcher than the module-grid in QRDetector. Uses spatial normalisation (de-rotation via minAreaRect) combined with two independent similarity scores averaged together. Used by MissionController as a fallback / secondary verifier. The MatchResult dataclass is also used throughout the system for HUD display.

Full match() Pipeline — 5 Phases

Ph1 → ILLUMINATION: grayscale + CLAHE (shared process_to_binary)
Ph2 → BINARISE: adaptiveThreshold Gaussian C=2 block=11
Ph3 → SPATIAL NORMALISE: findContours → largest → minAreaRect → de-rotate → crop → resize 128×128
Ph4 → SIMILARITY: pixel absdiff score + NCC matchTemplate → average
Ph5 → THRESHOLD: combined >= match_threshold (0.75) → MatchResult

Phase 3 — Spatial Normalisation Detail

contours = findContours(binary, RETR_EXTERNAL, CHAIN_APPROX_SIMPLE)
largest  = max(contours, key=cv2.contourArea)

rect_rot = cv2.minAreaRect(largest)
center, (rw, rh), raw_angle = rect_rot

# Fix angle: minAreaRect returns [-90, 0)
# If width < height, the box is "sideways" — add 90°
angle = raw_angle + 90 if rw < rh else raw_angle
# Normalise to (-45, +45]
while angle > 45:  angle -= 90
while angle <= -45: angle += 90

# De-rotate the entire binary image
M       = getRotationMatrix2D(center, angle, 1.0)
rotated = warpAffine(binary, M, ...)

# Crop the de-rotated bounding box
# Resize to 128×128 and re-binarise

Phase 4 — Combined Similarity Score

# Score 1: Pixel similarity (absdiff)
diff      = cv2.absdiff(img_a, img_b)        # per-pixel difference
mismatch  = np.count_nonzero(diff)           # count different pixels
pixel_sim = 1.0 - mismatch / img_a.size      # 1.0 = identical

# Score 2: Normalised Cross-Correlation (NCC)
a_f    = img_a.astype(float32) / 255.0
b_f    = img_b.astype(float32) / 255.0
result = cv2.matchTemplate(a_f, b_f, TM_CCOEFF_NORMED)
ncc    = max(0.0, float(result[0,0]))        # clamp negatives

# Combined: equal weight average
combined = (pixel_sim + ncc) / 2.0

Two independent scores from different mathematical approaches are averaged. This is more robust than either alone — NCC is good for structural similarity, pixel_sim penalises exact mismatches.

detectors/green_banner.py — Green Zone Detector

detectors/green_banner.py

Role

Detects green coloured objects/banners using HSV colour masking. Used as a physical waypoint marker in the mission area — when detected, the drone switches from corridor following to target search mode.

HSV Colour Sensing — Green Channel

The camera captures RGB. OpenCV converts to HSV (Hue-Saturation-Value) for colour detection because HSV separates colour (hue) from brightness (value), making detection lighting-robust.

H=40° lower
Hue: 40° (yellow-green)
Sat: 40 (pastel OK)
Val: 40 (dark OK)
H=60°
Mid-range green-yellow
H=80° upper
Hue: 80° (cyan-green)
Sat: 255 (full)
Val: 255 (bright)

The range H=40–80 covers yellow-greens through pure greens to cyan-greens. Sat minimum 40 prevents white/grey from matching. Val minimum 40 allows detection in shadow.

Detection Pipeline

1 → cv2.cvtColor(frame, COLOR_RGB2HSV) — note: input is RGB not BGR
2 → cv2.inRange(hsv, GREEN_LOWER, GREEN_UPPER) → binary mask
3 → morphologyEx MORPH_CLOSE with 5×5 kernel — fills small holes inside blobs
4 → morphologyEx MORPH_OPEN with 5×5 kernel — removes isolated noise pixels

detectors/red_zone.py — Red Danger Detector

detectors/red_zone.py

Role

Detects structured red ground markings that represent danger zones. Uses dual HSV ranges (because red wraps at 0°/180° in HSV) plus three shape filters to reject false positives from small red objects, thin lines, and irregular blobs.

Why Dual HSV Ranges for Red

The HSV hue channel is circular (0°–180° in OpenCV). Pure red appears at BOTH ends of the scale — around hue 0° and again at hue 170–180°. A single range would miss half of all red objects. Two ranges are OR-combined to catch all reds.

Range 1: H=0–10°
Lower red wrap
Sat: 100–255
Val: 100–255
Range 2: H=170–180°
Upper red wrap
Sat: 100–255
Val: 100–255
mask1 = cv2.inRange(hsv, lower1, upper1)   # hue 0–10
mask2 = cv2.inRange(hsv, lower2, upper2)   # hue 170–180
mask  = cv2.bitwise_or(mask1, mask2)       # combine both

Detection Pipeline

1 → cvtColor RGB→HSV
2 → inRange for both red ranges → OR merge
3 → morphologyEx OPEN with 7×7 kernel — removes small noise (larger than green's 5×5)
4 → morphologyEx CLOSE with 7×7 kernel — fills interior holes
5 → findContours RETR_EXTERNAL
6 → FILTER 1: area >= 5000 px² — rejects tiny red objects
7 → FILTER 2: solidity = area/convexHullArea >= 0.70 — rejects ragged/irregular shapes
8 → FILTER 3: aspectRatio = short/long >= 0.40 — rejects narrow lines/strips
9 → Compute centroid via moments M10/M00, M01/M00
10 → Append (cx, cy, area) sorted by area descending (most dangerous first)

Shape Filters Explained

AreacontourArea(cnt)>= 5000 px²Small random red pixels, lights, clothing
Solidityarea / convexHullArea>= 0.70 (70%)Thin lines, ragged vegetation edges, irregular blobs
Aspect Ratiomin(w,h) / max(w,h)>= 0.40Narrow strips, poles, thin markers

A 5m×5m red square viewed from altitude would pass all three filters. A red traffic cone or narrow banner would fail aspect ratio or solidity.

[(cx, cy, area), ...]   # sorted largest area first

detectors/corridor_nav.py — Corridor Navigator

detectors/corridor_nav.py

Role

Detects corridor walls using Canny edge detection on a central horizontal strip of the frame. Finds the rightmost left-wall edge and leftmost right-wall edge, computes corridor centre, and returns deviation from frame centre. This deviation drives LEFT/RIGHT correction commands.

Detection Pipeline

1 → cvtColor RGB→GRAY
2 → Canny(gray, 50, 150) — edge detection, thresholds 50 (weak) and 150 (strong)
3 → Crop ROI: only middle third of frame height (h/3 to 2h/3) — avoids ceiling/floor
4 → Left half ROI: columns 0 to w/2 — find rightmost edge pixel x
5 → Right half ROI: columns w/2 to w — find leftmost edge pixel x
6 → center_line = (left_edge_x + right_edge_x) / 2
7 → deviation = center_line - frame_width/2 (negative=left, positive=right)
8 → If no edges found: return (frame_width/2, 0) — centred fallback

Returns and Usage

(center_line, deviation)
# center_line: pixel x of detected corridor centre
# deviation: how far right of frame centre (+right, -left)

# Usage in mission_logic:
if abs(deviation) < CORRIDOR_CENTERED:  return "FORWARD"
if deviation > 30:                      return "RIGHT"
if deviation < -30:                     return "LEFT"

Canny Parameters

ParameterValueEffect
threshold1 (weak)50Edges with gradient > 50 are candidates
threshold2 (strong)150Edges with gradient > 150 are definite
ROI heightMiddle 1/3 of frameIgnores sky/ceiling and floor

Canny uses double thresholding: weak edges (50–150) are only kept if connected to strong (>150) edges. This rejects isolated noise while preserving wall edges.

draw_path() — Normalised → Pixel Conversion

def _norm_to_pixel(pt, width, height, margin):
    x_norm, y_norm = pt
    px = margin + x_norm * (width  - 2*margin)
    py = (height - margin) - y_norm * (height - 2*margin)
    # Note: y is INVERTED because pixel-y grows down, normalised-y grows up
    return int(px), int(py)

HSV Colour Sensing — Full Detail

Why HSV Instead of RGB

In RGB, a "green" object in bright light might be (50, 200, 50) but in shadow could be (10, 60, 10) — very different values even though it's the same green object. In HSV, the hue (colour) stays roughly constant while only value (brightness) changes. This makes HSV far more robust to lighting changes outdoors.

ChannelRange (OpenCV)Represents
H (Hue)0–180The colour itself (red=0, green=60, blue=120)
S (Saturation)0–255How vivid/pure (0=grey, 255=full colour)
V (Value)0–255Brightness (0=black, 255=bright)

Note: OpenCV uses H range 0–180 (not 0–360). Divide standard hue values by 2.

Green Detection Range Analysis

ParameterLowerUpperEffect
Hue40 (=80° real)80 (=160° real)Yellow-green through pure green to cyan-green
Saturation40255Allows pastel greens but rejects grey/white
Value40255Allows dark greens but rejects black

Morphology kernel: 5×5 ones. CLOSE then OPEN removes noise and fills holes.

Red Detection Range Analysis

RangeHueSaturationValueCatches
Lower wrap0–10100–255100–255Pure red, slightly orange-red
Upper wrap170–180100–255100–255Pure red, slightly purple-red

Saturation minimum 100 ensures only vivid reds are detected — prevents skin tones and pink objects from triggering. Value minimum 100 prevents very dark reds (shadows) triggering. Morphology kernel: 7×7 (larger than green's 5×5 — red zones are large structured objects).

CLAHE — Contrast Limited Adaptive Histogram Equalisation

Used in QR preprocessing (not HSV detection). Enhances local contrast in grayscale images to make QR modules more distinguishable in uneven lighting.

clahe = cv2.createCLAHE(clipLimit=2.0, tileGridSize=(8,8))
eq    = clahe.apply(gray)
# clipLimit=2.0 — max amplification factor per tile (prevents noise amplification)
# tileGridSize=(8,8) — image divided into 8×8 tiles, each equalised independently

Without CLAHE: a QR code in bright centre and dark edges would have modules that are not cleanly separated by a global threshold. With CLAHE: each region is enhanced locally making adaptive thresholding much more effective.

Template Matching — Full Technical Detail

Overview of Two Matching Systems

SystemLocationMethodUsed by
Module Grid Matcherqr_detector.pySample both to 29×29 grid, count agreements, try 4 rotationsMain matching — called every frame per candidate
NCC + PixelDiff Matchertemplate_matcher.pyDe-rotate via minAreaRect, pixel absdiff + NCC averagedMissionController fallback / secondary

Module Grid — Why 29×29

QR codes version 1 have 21×21 modules. Version 2 has 25×25. Version 3 has 29×29. By sampling at 29×29 we capture fine module detail for high-version QR codes while still being fast enough for real-time at 30fps on a Pi 4B. 841 comparisons per rotation × 4 rotations = 3364 operations total — extremely fast.

Why Rotation Check Matters

Drones can approach a landing zone from any direction. A QR code that was stored from the north may be seen from the south — rotated 180°. Without rotation checking, a rotated but otherwise identical QR would score only ~50% similarity (effectively random). By trying all 4 90° rotations and taking the best, we handle all approach angles.

Confidence Threshold — 0.75

The threshold of 0.75 means 75% of the 841 module cells must agree. This leaves 25% tolerance for: camera noise, perspective distortion, partial occlusion, lighting differences, and minor blur. A threshold too high (e.g. 0.95) would require near-perfect conditions and fail often. Too low (e.g. 0.50) would give false positives against random patterns.

Temporal Smoothing — Why 3 Frames

Even with a good threshold, a single frame might give a spurious match from a pattern that momentarily resembles the template. Requiring 3 consecutive True results means the match must persist for ~100ms at 30fps. This eliminates single-frame noise completely while still being fast enough for real-time decision making.

Future Improvements

1. Enable Boustrophedon Planner

Uncomment the planner import and build sections in vision_combined.py. Connect planner waypoints to actual motor commands (FORWARD for X metres, turn at row ends). This would give the drone systematic area coverage instead of relying purely on corridor following. Integrate with search_grid.py to mark visited cells.

2. MAVLink / DroneKit Integration

Currently the system outputs command strings (HOVER, FORWARD, DROP etc) to the screen and logs. The next step is to connect these to actual flight controller commands via MAVLink protocol using DroneKit or pymavlink. Each command string maps to a velocity setpoint or position command sent to the flight controller via UART/USB.

3. GPS-Aided Navigation

Add GPS module (u-blox NEO series) to Raspberry Pi. Implement gps_to_cell() in search_grid.py using haversine distance formula. Use GPS for coarse navigation to search area and camera-based methods for fine alignment at the target. GPS home position stored at startup for RETURN_HOME.

4. Wire Sharpness Check

QRDetector already accepts sharpness_min parameter. Add Laplacian variance calculation to detect() and set is_sharp = (variance >= sharpness_min) in the returned 6-tuple. This will automatically reject blurry QR detections caused by motion blur or focus lag during fast movement. Currently all detections pass regardless of sharpness.

5. YOLO Integration into Main Mission

Add YOLO detection as an optional fifth detector in vision_combined.py. Use it to detect the drop zone marker (e.g. a person, vehicle, or specific object class) at long range before QR codes are readable. YOLO provides coarse target acquisition, QR matching provides precise verification. Add YOLO_ENABLED flag to config.py.

6. Altitude Control via Optical Flow

Add a second camera or use the existing camera with optical flow (cv2.calcOpticalFlowFarneback) to estimate ground speed and altitude changes. Feed this into a PID controller for constant-altitude corridor following. Currently altitude is assumed constant.

7. Multi-Target Support

Extend QR payload format to carry multiple template images or a target identifier list. MissionController would then iterate through multiple drop zones in sequence. The state machine would add a NEXT_TARGET state between DROP_READY and RETURN_HOME.

8. Web Dashboard / Telemetry

Add a Flask or FastAPI server running on the Pi that streams the live frame via MJPEG, exposes mission state as JSON, and allows mission override commands via HTTP. Log files could be served in real-time. All within vision_combined.py's finally block for clean shutdown.

9. PID-Based Corridor Following

Replace the simple threshold-based LEFT/RIGHT/FORWARD commands with a PID controller using corridor deviation as the process variable. This would give proportional corrections instead of binary ones — smoother flight and less oscillation when following corridor walls.

10. Dataset Auto-Collection Mode

Add a DATASET_MODE flag to config.py. When True, every detected and matched QR pair (template + candidate + binary crops + confidence + metadata) is saved automatically with structured filenames. This would build a training dataset for a future CNN-based matcher that could replace the module-grid approach.

11. Night / Low-Light Mode

Add IR LED ring to illuminate the search area. Adjust CLAHE parameters (higher clip limit) and Canny thresholds (lower to detect weak edges) for night conditions. Add a DAY_MODE / NIGHT_MODE config flag that selects different HSV ranges and preprocessing parameters automatically based on mean frame brightness.

12. Confidence Calibration and Logging

After many flights, plot confidence distributions for true matches vs false positives. Use this to tune MATCH_THRESHOLD more precisely per environment. Add per-run confidence histogram saved as PNG to the output folder. Long-term: adaptive threshold that adjusts based on observed false positive rate.
